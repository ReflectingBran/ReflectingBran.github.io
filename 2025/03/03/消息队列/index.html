消息队列概述

消息队列是大型分布式系统不可缺少的中间件，也是高并发系统的基石中间件。它指的是一个保存消息的容器，本质上就是一个保存数据的队列。

中间件是一类为应用软件服务的软件。

消息中间件是指利用高效可靠的消息传递机制进行与平台无关的数据交流，并基于数据通信来进行分布式系统的构建。
消息中间件是分布式系统中重要的组件，主要解决应用解耦，异步消息，流量削峰等问题，实现高性能，高可用，可伸缩和最终一致性的系统架构。目前使用较多的消息队列有 ActiveMQ， RabbitMQ， ZeroMQ， Kafka， MetaMQ， RocketMQ 等。

  • 异步处理（将一些非核心的业务流程以异步并行的方式执行，减少请求响应时间，提高系统吞吐量）
    • 例如电商系统中，用户下单后需要生成订单、赠送积分、赠送红包、发布下单成功通知等，若串行执行各任务，显然不如并行执行效率高，这样就大大提高了系统的吞吐量
  • 应用解耦（通过消息队列，解除应用系统之间的耦合依赖，使得每个应用系统不必受其他系统影响，可以更独立自主）
    • 例如电商系统中，用户下单后，订单系统需要通知积分系统，若订单系统直接调用积分系统的接口，这样就使得应用系统之间的耦合特别紧密，如果积分系统无法访问，那么积分处理失败则会导致订单失败。但加入消息队列后，当用户在订单系统完成下单后，消息则会被写入消息队列，返回用户订单下单成功。积分系统通过订阅下单消息的方式获取下单通知消息，从而进行积分操作。实现订单系统与积分系统的应用解耦。如果在下单时积分系统异常，也不影响用户正常下单，因为下单后，订单系统写入消息队列就不再关心其他的后续操作
  • 流量削峰
    • 例如电商系统中，若出现秒杀或者团抢活动，一般会因为流量过大，导致流量暴增，应用崩溃。但加入消息队列后，秒杀业务处理系统可以根据消息队列中的请求信息，再做后续业务处理，假设消息队列长度超过最大数量，则直接抛弃用户请求或者跳转到错误页面
  • 消息通讯（指的是应用间的数据通信）
    • 消息队列一般都内置了高效的通信机制，因此也可以用在纯的消息通讯。比如实现点对点消息队列，或者聊天室等点对点通讯

消息队列使用发布-订阅模式工作，消息发送者（生产者）发布消息，一个或多个消息接受者（消费者）订阅消息。 消息发送者将消息发送至分布式消息队列即结束对消息的处理，消息接受者从分布式消息队列获取该消息后进行后续处理，并不需要知道该消息从何而来。对新增业务，只要对该类消息感兴趣，即可订阅该消息，对原有系统和业务没有任何影响，从而实现网站业务的可扩展性设计（应用解耦）。

例如，我们商城系统分为用户、订单、财务、仓储、消息通知、物流、风控等多个服务。用户在完成下单后，需要调用财务（扣款）、仓储（库存管理）、物流（发货）、消息通知（通知用户发货）、风控（风险评估）等服务。使用消息队列后，下单操作和后续的扣款、发货、通知等操作就解耦了，下单完成发送一个消息到消息队列，需要用到的地方去订阅这个消息进行消息即可。

虽然消息队列应用场景广泛，但盲目使用消息队列仍然会带来一些问题：

  • 系统可用性降低：加入消息队列后，需要考虑消息丢失或者消息队列自身崩溃等情况
  • 系统复杂性提高：加入消息队列后，需要保证消息没有被重复消费，还需要处理消息丢失，需要保障消息传递的顺序性
  • 一致性问题：消息队列带来的异步确实可以提高系统响应速度，但是如果真正的消费者没有正确消费消息，则会导致数据不一致的问题

如何实现消息的百分之百可靠性发送

在使用消息队列时，由于生产者和消费者不直接交互，所以面临着几个问题：

  • 要把消息添加到队列中，怎么保证消息成功添加
  • 如何保证消息发送出去时一定会被消费者正常消费
  • 消费者正常消费了，生产者或者队列如何知道消费者已经成功消费了信息

RabbitMQ怎样实现的消息百分之百可靠性发送

RabbitMQ 提供了消息百分百可靠性发送的解决方案，以电商系统中的创建订单为例，实现百分百可靠性发送需要以下条件：

  • 完成订单业务处理后，生产者发送一条消息到消息队列，同时记录这条操作日志（发送中）
  • 消费者收到消息后处理进行
  • 消费者处理成功后给消息队列发送 ack 应答
  • 消息队列收到 ack 应答后，给生成者的 Confirm Listener 发送确认
  • 生产者对消息日志表进行操作，修改之前的日志状态（发送成功）
  • 在消费端返回应答的过程中，可能发生网络异常，导致生产者未收到应答消息，因此需要一个定时任务去提取其状态为“发送中”并已经超时的消息集合
  • 使用定时任务判断为消息事先设置的最大重发次数，大于最大重发次数就判断消息发送失败，更新日志记录状态为发送失败

如何保证消息没有重复消费？使用消息队列如何保证幂等性

幂等性：用户对于同一操作发起的一次请求或者多次请求的结果总是一致的，不会因为多次点击而产生了副作用问题出现原因。
消息产生重复消费的原因：

  • 生产者可能会推送重复的数据到消息队列中，有可能 controller 接口重复提交了两次，也可能是重试机制导致的
  • 网络出现了波动，消费者消费完一条消息后，发送 ack 时，消息队列还没来得及接受，突然挂了，导致消息队列以为消费者还未消费该条消息，消息队列回复后会再次推送了这条消息，导致出现重复消费
  • 消费者接收到消息后，正准备发送 ack 到消息队列，突然消费者挂了，还没得及发送 ack，这时消息队列以为消费者还没消费该消息，消费者重启后，消息队列再次推送该条消息

在正常情况下，生产者是客户，很难避免出现用户重复点击的情况，而消息队列是允许存在多条一样的消息，但消费者是不允许出现消费两条一样的数据，所以幂等性一般是在消费端实现的。

解决方案之状态判断：消费者把消费消息记录到 redis 中，再次消费时先到 redis 判断是否存在该数据，存在则表示消费过，直接丢弃。
解决方案之业务判断：消费完数据后，都是需要插入到数据库中，使用数据库的唯一约束防止重复消费。插入数据库前先查询是否存在该数据，存在则直接丢弃消息，这种方式是比较简单粗暴地解决问题。

消息丢失怎么办

消息丢失属于比较常见的问题。一般有生产端丢失、消息队列服务丢失、消费端丢失等三种情况。针对各种情况应对方式也不一样。
生产端丢失的解决方案：

  • 开启 confirm 模式，生产者收到消息队列发回的 confirm 确认之后，再进行消息删除，否则消息重推
  • 生产者端消息保存的数据库，由后台定时程序异步推送，收到 confirm 确认则认为成功，否则消息重推，重推多次均未成功，则认为发送失败

消息队列服务丢失的解决方案：

  • 开启消息持久化，让消息及时保存到磁盘

消费端丢失的解决方案：

  • 关闭自动 ack 确认，消息消费成功后手动发送 ack 确认；消息消费失败，则重新消费

消息的传输顺序

在生产端发布消息时，每次发布消息都把上一条消息的 ID 记录到消息体中，消费者接收到消息时，做如下操作：

  • 先根据上一条 ID 去检查是否存在上一条消息还没被消费，如果不存在(消费后去掉 ID )，则正常进行，如果正常操作
  • 如果存在，则根据 ID 到数据库检查是否被消费，如果被消费，则正常操作
  • 如果还没被消费，则休眠一定时间(比如 30 ms )，再重新检查，如被消费，则正常操作
  • 如果还没被消费，则抛出异常

消息积压问题

所谓的消息积压，就是生产者生产消息太快，而消费者处理消息太慢，从而导致消费端消息积压在消息队列中无法处理的问题。遇到这种消息积压的情况，可以根据消息重要程度，分为两种情况处理：

  • 如果消息可以被丢弃，那么直接丢弃就好了
  • 一般情况下，消息是不可以被丢弃的，那么这样需要考虑策略了，我们可以把原来的消费端重新当做生产端，重新部署消息队列，再后面出现增加消费端，这样形成另一条生产-消息-消费的线路
